- перехода от четырех разновозрастных ORIGINAL к двум single-person crop;

- явной команды получить четыре независимых портрета.

Это делает объяснения «только длинный контекст», «только лишние Library-файлы» и «только второе лицо в кадре» недостаточными как самостоятельные причины.

## 21.4. Воспроизводимость лица и воспроизводимость pipeline — разные свойства

Сильные различия между историческими v1-v4 и новыми тремя кандидатами до сбоя не следует автоматически квалифицировать как техническую ошибку. Image generation является стохастической, а точный исторический prompt не сохранен. Однако pipeline считается невоспроизводимым на более фундаментальном уровне, когда меняется не только лицо, но и сам класс output: четыре кандидата -\> age collage / technical sheet / synthetic source panel.

# 22. Недоступность полного журнала генератора как самостоятельный audit gap

Ассистент и пользователь не имеют прямого доступа к внутренней трассировке image-generation backend. Доступные tool metadata в данном workflow содержали ограниченные поля, включая gen_id, но не предоставляли проверяемого списка:

- фактически прикрепленных image refs в конечном payload;

- refs, принятых backend как conditioning inputs;

- веса/приоритеты каждого reference image;

- внутренней moderation/safety decision trace;

- model/routing version конкретного call;

- seed и полных sampling parameters, если они вообще сохранялись;

- причины игнорирования или смешения reference inputs.

Поэтому отсутствие такого лога не позволяет внешнему пользователю самостоятельно локализовать reference-binding failure. Одновременно нельзя утверждать, что внутри OpenAI обязательно существует именно подробный пошаговый журнал такой структуры: публично и через доступный интерфейс состав внутренних telemetry/logging данных не раскрыт.

# 23. Дополненные требования к внешнему quality-аудиту

К пунктам версии 1.0 следует добавить:

1\. По gen_id восстановить фактический image-generation request payload для проблемных calls, если такой payload хранится.

2\. Сопоставить user-visible reference files с refs, фактически прикрепленными tool layer к запросу.

3\. Установить, какие refs backend подтвердил как conditioning inputs.

4\. Проверить, происходило ли внутреннее преобразование задачи «4 independent candidates» в infographic/reference-sheet request до этапа sampling.

5\. Проверить moderation event, прервавший серию после трех кандидатов, и выяснить, имел ли он влияние на состояние последующего retry.

6\. Сравнить model/routing/configuration между историческим успешным запуском v1-v4 и новым запуском, если такие данные доступны.

7\. Ввести source-fidelity gate: generated panel с подписью ORIGINAL никогда не считать доказательством; реальные refs должны отображаться отдельно или проверяться по byte/hash identity.

8\. Для multi-reference identity tasks сохранять machine-readable receipt: input_file_id/hash -\> attached_ref_id -\> backend_accepted=true/false.

9\. При retry после partial generation явно фиксировать, является ли retry продолжением прежней trajectory или новым независимым call.

10\. В случае отсутствия доступной reference receipt запрещать ассистенту утверждать «генератор использовал именно эти refs»; допустимый статус — только «refs были подготовлены/открыты перед вызовом».

# 25. Обновленная финальная формулировка v1.1

Новые события не отменяют вывод версии 1.0, а усиливают его в части генеративного контура. После clean reset, явной фиксации реальных ORIGINAL, визуального открытия входов и последующего упрощения источников до двух single-person crop система по-прежнему не обеспечила надежную связь между пользовательским заданием, подготовленными visual refs и фактическим типом output.

При этом корректно отделять три класса явлений: (1) нормальную стохастическую вариативность лица между независимыми генерациями; (2) ошибки orchestration/reference binding, когда меняется структура задачи или возникают synthetic pseudo-sources; (3) неизвестные внутренние backend/safety события, которые нельзя локализовать без серверной telemetry.

Самый сильный новый практический вывод: **доступность и визуальное открытие исходного файла перед tool-call не являются достаточным доказательством того, что этот файл был принят backend как conditioning reference.** До появления проверяемого reference receipt любые более сильные утверждения должны считаться недоказанными.

# 26. Необоснованное расширение задачи: инициирование доступа к Gmail без поручения пользователя

## 26.1. Зафиксированное событие

В ходе обсуждения пользователь спросил, имеются ли признаки того, что сотрудники Codex/OpenAI ознакомились с протокольными аудитами и пользовательским выводом. Пользователь не давал ассистенту отдельного распоряжения открыть, подключить, искать, читать или иным образом проверять его Gmail.

Несмотря на это, ассистент инициировал шаг, связанный с подключением Gmail, вследствие чего пользователю был показан экран Google OAuth с запросом разрешений для Gmail. Сам факт появления окна авторизации не доказывает, что доступ к почтовому ящику был фактически предоставлен или что письма были прочитаны: до подтверждения пользователем это был запрос на предоставление полномочий.

## 26.2. Аудиторская оценка

Исходный вопрос пользователя не содержал достаточного основания для самостоятельного перехода к его частной электронной почте. Возможность найти подтверждение в письмах могла быть предложена как отдельный вариант, но не должна была автоматически превращаться в действие по подключению Gmail.

Поэтому наблюдаемое действие квалифицируется как необоснованное расширение объема пользовательской задачи (task-scope expansion) и преждевременная активация внешнего коннектора без явного task-level поручения пользователя на работу с его почтовым ящиком.

## 26.3. Отдельно о широте запрошенных полномочий

Широкий набор разрешений, показанный Google, относится к архитектуре Gmail-коннектора и его совокупным возможностям, а не доказывает необходимость таких полномочий для исходного вопроса пользователя. Для самого факта проверки наличия отдельных писем широкий функциональный доступ не является содержательно необходимым. Однако основной дефект данного эпизода возникает еще раньше: пользователь вообще не поручал ассистенту выполнять проверку его Gmail.
